# Scrave 문제·경험·홍보·사업 모델 기획

2026-10-09 현재 대화에서 사용자가 설명한 캡처 습관을 기준으로 작성했습니다. 고객 인터뷰 결과나 구현 완료 보고가 아닌 기획 제안입니다. [경험과 장면 기획판](../../_dogfood/2026-10-09_scrave_saved-information-experience_v2.html)에서 네 장면을 비교할 수 있습니다.

## 1. 이번에 구체화한 문제

사용자는 원래 서비스에 로그인하고 예약을 찾아 다른 앱에 옮기는 여러 단계를 피하려고 캡처합니다. 이후에도 캡처 속 링크를 누를 수 없거나, 장소 이름을 몰라 검색하고 후기를 확인한 뒤 지도에 다시 저장합니다. Scrave는 그 후속 작업을 이어받아 사용자가 필요한 내용을 한곳에서 다시 보게 합니다. 한 번 질문하거나 검색해서 얻은 결과도 출처와 함께 저장하며, 다시 볼 때 같은 질문을 반복할 필요가 없도록 합니다. [High: 사용자 직접 설명]

전체 흐름은 캡처 → 원본 보관 → 정보 추출 → 필요한 검색·후기 확인 → 내부 저장 → 재사용으로 잡습니다. 입력마다 검색하지 않고, 예약 서류처럼 원본을 바로 꺼내는 것이 중요한 자료와 장소를 알아내야 하는 자료를 구분합니다. 지도 앱으로 내보내거나 저장하는 기능은 선택 사항이며 후속 범위로 둡니다.

## 2. 해결할 문제의 우선순위

| 순서 | 사용 순간과 불편 | Scrave의 결과 | 판단 근거와 한계 |
|---|---|---|---|
| 먼저 검증합니다 | 공항 입구에서 항공 예약을 보여 달라고 합니다. 앱 로그인이 풀렸고 인터넷도 느립니다. | 기기에 보관한 예약 원본을 바로 확대합니다. 항공·숙소·식당 예약·비자를 같은 여행 묶음에서 엽니다. | 사용자가 직접 겪은 사례입니다. 입장 규정이나 캡처의 증빙 효력을 보장하지 않습니다. |
| 다음으로 검증합니다 | 게시물의 장소 이름이 없고 메시지를 보내라고 합니다. 캡처 후 검색·후기 확인·지도 저장을 반복합니다. | 공개된 단서로 장소 후보를 찾고 출처·후기·주소와 원본을 함께 남깁니다. | 사용자가 직접 설명한 행동입니다. 불확실한 후보를 확정하거나 비공개 정보를 우회하지 않습니다. |
| 같은 구조로 넓힙니다 | 방문 시각은 문자, 층수·주차 안내는 링크에 있습니다. | 방문에 필요한 자료와 원본을 한 묶음으로 봅니다. | 사용자 예약 사례를 일상으로 확장한 가설입니다. 실제 빈도를 조사해야 합니다. |
| 후속으로 검증합니다 | 전에 물어본 사용법을 또 묻고 조건을 다시 설명합니다. | 질문·조건·답변·원문을 다시 볼 화면으로 저장합니다. | 사용자가 설명한 반복 질문 문제를 적용했습니다. 저장된 답변과 검증된 사실을 구분합니다. |
| 보류합니다 | 상품 후보와 후기를 여러 곳에서 비교합니다. | 제품 식별·비교 근거·선택 이유를 보관합니다. | 비교 기능은 가능한 확장입니다. 현재 가격·재고와 과거 캡처를 구분해야 합니다. |
| 기록이 쌓인 후 검증합니다 | 좋아했던 자료와 새로운 추천을 연결하고 싶습니다. | 사용자가 확인한 이유와 선택을 근거로 추천합니다. | 모든 저장을 선호나 구매 의도로 해석하지 않습니다. |

추천은 일상 자료를 받는 제품으로 설계하되, 첫 홍보와 실제 사용 검증을 여행의 긴급 재확인 장면에 집중하는 것입니다. 예약번호 조회만으로는 기존 지갑 앱과 구별하기 어려우므로, 서비스가 서로 다른 원본을 함께 보관하고 즉시 제시하는 흐름을 검증합니다. [Medium: 전략 제안]

## 3. 기억할 약속과 표현 후보

이번 사용자가 원하는 가치는 ‘필요한 내용을 한곳에서 본다’입니다. 제품 설명은 ‘캡처한 내용을 바로 쓸 수 있게 모읍니다’를 후보로 제안합니다. 저장·분류 자체보다 캡처 뒤에 반복하던 일을 보여 주며 설명합니다. 문구는 아직 확정하지 않았습니다.

| 용도 | 문구 후보 | 보여 줄 근거 |
|---|---|---|
| 전체 제품 설명 | 캡처한 내용을 바로 쓸 수 있게 모읍니다. | 원본 옆에 추출 정보·링크·찾은 자료가 함께 있습니다. |
| 여행 장면 | 예약을 보여 달라는 순간, 캡처해 둔 원본을 바로 엽니다. | 인터넷 연결 없이 기기에 저장한 원본을 여는 실제 시연이 필요합니다. |
| 장소 발견 장면 | 캡처에서 장소를 찾고, 확인한 후기를 함께 남깁니다. | 실제 장소 식별과 출처 대조가 필요합니다. |
| 답변 재사용 장면 | 한 번 정리한 답변은 다음에도 꺼내 봅니다. | 앱 재실행 뒤 같은 결과와 근거를 여는 시연이 필요합니다. |

‘캡처만 하면 무엇이든 해결’, ‘자동으로 내 취향을 안다’, ‘로그인이 영원히 필요 없다’는 약속을 하지 않습니다. 정보를 올바르게 식별하지 못하는 경우와 실시간 확인이 필요한 항목을 제품 설명에 반영합니다.

## 4. 경험 설계

### 입력과 권한

처음에는 사용자가 고른 캡처를 가져와 바로 가치를 보여 줍니다. 이미 허용한 범위에서 새로운 캡처를 읽는 흐름은 운영체제 권한에 맞춰 별도 검증합니다. 스크린샷 유형을 고르는 기능과 ‘앞으로 찍는 모든 스크린샷에만 접근’하는 권한은 구분해야 합니다. Apple의 제한 사진 접근은 사용자가 고른 사진을 대상으로 하며, 스크린샷만 표시하는 선택 필터는 별도 기능입니다. 전체 사진 권한을 받은 뒤 앱이 스크린샷만 처리한다면 그 사실을 정확하게 안내합니다. [Apple 제한 접근](https://developer.apple.com/videos/play/wwdc2020/10641/) · [스크린샷 선택 필터](https://developer.apple.com/documentation/photosui/phpickerfilter-c.class/screenshotsfilter)

사진 접근, 외부 인공지능 전송, 개인 추천, 광고 목적 활용은 하나의 동의로 묶지 않습니다. 입력 자료를 얻을 권한만으로 외부 전송과 상업적 활용까지 허용됐다고 간주하지 않습니다. 사용자가 계정 전체를 연결하지 않아도 캡처를 입력할 수 있어야 합니다.

### 두 가지 처리 경로

예약·비자·입장 자료는 먼저 원본을 기기에 보관하고, 광학 문자 인식(OCR, 이미지 속 글자를 읽는 기술)과 QR 코드 판독으로 주소·날짜·링크 같은 필드를 추출합니다. 이 단계는 기기에서 처리하는 방식을 우선 검토합니다. 원본이 아이클라우드에만 있다면 내려받기 완료 전에는 오프라인 준비 완료로 표시하지 않습니다. Apple Vision은 이미지의 텍스트·바코드 인식을 지원하지만 실제 캡처와 언어별 인식 품질은 별도 시험이 필요합니다. [Apple 이미지 인식](https://developer.apple.com/documentation/vision/detecting-objects-in-still-images)

궁금한 장소·상품은 기기에서 추출한 공개 단서를 토대로 온라인 검색을 제안합니다. 외부 검색에는 필요한 단서만 사용하고 예약번호·여권 정보·개인 대화 전체를 보내지 않습니다. 이름이 불확실하면 후보와 근거를 보여 주며, 확인한 대상의 후기만 연결합니다. 네이버·구글·유튜브·인스타그램의 모든 내용을 읽을 수 있다고 약속하지 않고, 사용이 허용된 검색 방식과 출처 링크부터 제공합니다. 사용자가 게시물 작성자에게 메시지를 보냈다고 가장하거나 비공개 답변을 얻은 것처럼 표시하지 않습니다.

두 경로 모두 첫 저장을 검색 완료에 의존시키지 않습니다. 원본 보관, 분석 대기, 검색 대기, 후보 확인, 자료 준비의 상태를 구분하고 네트워크가 돌아왔을 때 중복 없이 이어 갑니다. 자동 외부 분석의 비용·호출 상한은 구현 전에 별도 결정합니다.

### 한곳에서 다시 보기

홈은 대화 입력창보다 고정한 여행·방문 묶음과 최근 캡처를 먼저 보여 줍니다. ‘이번 여행’ 묶음 안에서 항공·숙소·식당·비자 원본을 바로 열며, 확대할 때 이미지의 글자와 코드가 잘리지 않도록 합니다. 원본과 정리 정보는 같은 화면에서 오갈 수 있게 합니다.

예약번호 복사, 판독한 주소·전화번호 사용, 원문 링크 열기, 원본 확대를 핵심 행동으로 둡니다. 원문에 주소가 없다면 검색으로 찾은 주소라는 사실을 표시합니다. 링크를 읽었다고 외부 사이트 로그인이 사라지는 것은 아니며, 민감한 동작을 포함하는 코드나 링크는 미리 확인한 뒤 엽니다.

대화는 저장 자료를 사용하는 보조 기능입니다. 답변에 근거와 확인일을 붙이고 사용자가 다시 볼 내용으로 저장할 수 있게 합니다. 반복해서 화면을 여는 행위는 재생성·재과금의 계기가 되지 않게 설계합니다. 수정한 답변은 이전 근거와 연결을 유지합니다.

### 오프라인과 최신성

오프라인 대상은 기기에 저장 완료한 원본·추출 정보·허용된 저장 결과입니다. 외부 링크 열기·새 검색·실시간 변경 조회는 네트워크가 필요합니다. 여행 묶음별로 원본 다운로드 상태를 보여 주고 비행기 모드에서 앱을 종료·재실행해도 여는지 확인합니다.

캡처 시각과 마지막 확인 시각을 구분합니다. 지연·탑승구·예약 취소·회전형 QR 코드는 정적인 캡처만으로 갱신할 수 없습니다. 일반 사진의 QR을 새로 만들어 원본을 대체하지 않으며, 입장 가능 여부도 별도로 취급합니다. Apple Wallet은 지원되는 탑승권에 실시간 항공 정보를 제공하므로, 이 영역을 Scrave만의 기능처럼 홍보하지 않습니다. [Apple Wallet 설명](https://developer.apple.com/videos/play/wwdc2025/202/)

## 5. 홍보 장면 구성

홍보의 첫 장면은 실제 불편이 나타난 순간을 사용합니다. 지금 기획판의 텍스트는 촬영 구성이며 실제 제품 시연이나 고객 결과가 아닙니다. 개인정보가 담긴 실제 서류는 동의와 가림 처리 없이 촬영·공개하지 않습니다.

| 장면 | 여행 자료 편 | 장소 검색 편 | 답변 재사용 편 |
|---|---|---|---|
| 필요가 생깁니다 | 입구에서 예약 내역을 보여 달라고 합니다. | 장소 이름을 알고 싶은데 게시물에는 메시지를 보내라는 문구가 있습니다. | 전에 해결했던 문제가 다시 생깁니다. |
| 불편을 보여 줍니다 | 느린 인터넷·로그인·사진첩 탐색을 실제 과정대로 보여 줍니다. | 캡처를 검색하고 후기 앱을 오가며 다시 저장합니다. | 어느 대화였는지 찾다가 조건을 다시 설명합니다. |
| Scrave의 일을 보여 줍니다 | 이미 보관한 여행 묶음을 열어 원본을 확대합니다. | 같은 캡처 옆에 장소 후보와 확인 근거·후기를 보여 줍니다. | 저장된 답변과 적용 조건·근거를 엽니다. |
| 결과를 보여 줍니다 | 필요한 원본을 바로 제시합니다. 실제 입장 승인 장면은 별도 증거가 있어야 합니다. | 다음 방문에 저장된 장소 정보를 다시 엽니다. | 다시 묻지 않고 확인한 내용을 사용합니다. |

첫 광고 소재로는 여행 자료 편을 추천합니다. 사용자가 직접 겪은 장면이고, 검색 결과의 정확도를 설명하기 전에 원본이 바로 열리는 결과를 시각적으로 보여 줄 수 있기 때문입니다. 두 번째 소재에서 캡처의 단서가 장소·후기로 이어지는 흐름을 검증합니다.

## 7. 기존 기능과 개발할 부분

원격 `c2d7a7f`에는 캡처·장소·지도·가이드 관련 코드가 있고, `CaptureItem`에 추출 텍스트·링크·원본 이미지 주소가 있습니다. 장소 후기 관련 코드도 확인했습니다. 이는 재사용 후보이며 현재 운영 품질이나 오프라인 동작을 검증한 결과가 아닙니다.

첫 구현 전에 원본의 로컬 보관과 재실행, 사진 권한별 입력, 여행 묶음, 원본 확대, 판독 링크, 처리 대기 상태를 확인해야 합니다. 그다음 장소 식별·후기 수집의 허용 경로와 비용을 정합니다. 기존 작품 분석 상세 화면은 병행 세션이 맡고 있으므로 같은 파일을 중복 수정하지 않습니다.

검증은 순서대로 진행합니다. 첫째, 권한을 거부하거나 선택 사진만 허용해도 안내와 입력이 작동해야 합니다. 둘째, 인터넷 없이 저장 원본을 열고 확대할 수 있어야 합니다. 셋째, 작은 글자·날짜·시차·중복 캡처·판독 실패를 원문과 대조합니다. 넷째, 실제 장소를 잘못 확정하지 않고 후보를 고칠 수 있어야 합니다. 마지막으로 며칠 후 다시 열 때 사용자가 검색과 로그인 과정을 얼마나 반복하는지 관찰합니다. 소수 관찰로 시장 비율을 만들지 않습니다.

## 8. 광고와 데이터 활용의 사업 가능성

관심 있는 장소·상품을 찾아 확인하고 저장하는 흐름에는 추천과 구매 연결의 사업 가능성이 있습니다. 다만 사용자가 캡처했다는 사실은 구매 의도나 선호의 확정 신호가 아니며, 사업성이 입증된 상태도 아닙니다. [Medium: 사업 가설]

| 모델 | 가능한 설계 | 현재 권고 |
|---|---|---|
| 유료 기능·구독 | 기기 간 동기화·고급 검색·정리 등 반복 가치를 검증합니다. | 먼저 지불 의사를 조사합니다. 구체 가격과 비용은 아직 정하지 않았습니다. |
| 제휴 추천·예약 연결 | 사용자가 추가 후보를 찾을 때 광고·제휴임을 표시하고 선택하게 합니다. | 원본 서류 보기나 자연 검색 결과를 광고 때문에 방해하지 않는 방향으로 검토합니다. |
| 집계된 수요 조사 | 개인을 알아볼 수 없는 집계 설계와 법적 근거를 별도로 검토합니다. | 동의·재식별 위험·플랫폼 조건·통계 편향을 확인한 뒤 판단합니다. |
| 개인별 캡처·관심 프로필 제공 | 제공받는 자와 목적·항목·기간을 특정해야 하며 타인의 정보와 민감한 내용이 섞일 수 있습니다. | 제품의 기본 수익 모델로 삼지 않는 편을 추천합니다. |

한국에서 동의에 근거해 개인정보를 제3자에게 제공하려면 받는 자, 이용 목적, 제공 항목, 보유·이용 기간, 거부권과 불이익 등을 알려야 합니다. 포괄적인 ‘마케팅 동의’만으로 임의의 업체에 캡처를 제공할 수 있다고 가정하지 않습니다. [개인정보 보호법 제17조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029335261)

Apple은 외부 인공지능을 포함한 제3자 개인정보 공유를 명확히 알리고 사전 허락을 받도록 요구하며, 사진 등에서 얻은 정보로 연락처 데이터베이스를 만들어 판매·배포하는 행위를 금지합니다. 다른 앱·웹사이트의 정보와 결합하는 추적에는 별도 조건도 적용됩니다. 따라서 동의만 받으면 모든 데이터 거래가 가능하다는 전제로 사업을 설계하지 않습니다. 광고 추적 요건과 실제 계약 가능 여부는 구현할 모델을 특정한 뒤 전문가와 검토해야 합니다. [Apple 개인정보·공유 규정](https://developer.apple.com/app-store/review/guidelines/#privacy)

권장 구조는 개인 원본과 개인 분석을 사용자 서비스 영역에 두고, 광고주에게는 원본·예약번호·비자·개별 이동 내역을 전달하지 않는 것입니다. 사용자가 추천을 요청한 순간에 제휴 제안을 표시하는 방식부터 검토하며, 제공처와 수집 항목에 따라 별도 동의·정책 검토를 진행합니다. 원본 문서 화면에는 광고를 넣지 않는 방향을 제안합니다.

## 9. 이번 산출물의 검증과 범위

경험 기획판은 설명용 자료이며 실제 예약·캡처를 분석하지 않습니다. 장면 전환, 예시 저장, 근거 대화창만 로컬에서 동작합니다. 기존 앱과 계정·지도·인공지능 서비스를 연결하거나 유료 호출·광고 집행을 하지 않았습니다. 디자인·문체·브라우저 동작을 검사하고 기록을 작업판에 남깁니다.
