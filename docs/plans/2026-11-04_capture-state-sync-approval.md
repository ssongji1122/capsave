# 캡처 사용자 상태 동기화 결재안

작성일: 2026-11-04
상태: 설계 완료 · 마이그레이션 작성/적용 전
적용 대상: Scrave 웹·Expo 모바일·기존 Supabase

## 해결할 문제

로그인 캡처의 원본과 AI 분석 결과는 서버 `captures`에 저장되지만, 아래 사용자 상태는 기기에만 남습니다.

- 저장 이유, 메모, 다시 볼 시점, 여행 묶음 고정, 행동 완료 상태
- 캡처별 스티커 배치
- 웹은 `localStorage`, 모바일은 계정별 파일과 SQLite 키-값 저장소를 사용합니다.

따라서 같은 계정으로 웹과 모바일을 오가면 사용자가 직접 만든 상태가 이어지지 않습니다. 현행 `captures` 행에 이 값을 바로 넣으면 분석 결과 수정과 사용자 메타 수정이 같은 충돌 범위를 공유하므로 별도 상태 테이블이 적합합니다.

## 권장 구조

기존 `captures`는 변경하지 않고 두 보조 테이블을 추가합니다.

### `capture_user_metadata`

- 기본키: `(user_id, capture_id)`
- 값: `reasons`, `note`, `revisit`, `revisit_on`, `pinned_to_travel_pack`, `completed_actions`
- 충돌 제어: `revision`, `updated_at`
- 제한: 메모 600자, 허용된 이유·다시 보기 값만 저장

### `capture_decorations`

- 기본키: `(user_id, capture_id)`
- 값: 정규화한 스티커 배치 JSON 배열
- 충돌 제어: `revision`, `updated_at`
- 제한: 최대 20개, 스티커 번호·좌표·크기·회전 범위 검사

두 테이블 모두 `capture_id`를 `captures.id`에 연결하고, RLS(Row Level Security, 행 단위 접근 제어)에서 로그인 사용자와 캡처 소유자가 모두 일치할 때만 읽고 쓸 수 있게 합니다. 관리자용 우회 키를 클라이언트에 넣지 않습니다.

## 충돌 처리

마지막 저장 우선 방식은 다른 기기의 편집을 조용히 덮어쓸 수 있어 사용하지 않습니다.

1. 클라이언트가 읽은 `revision`을 저장 요청에 함께 보냅니다.
2. 서버 값과 revision이 같을 때만 갱신하고 1을 더합니다.
3. 값이 다르면 서버 상태를 다시 받아 충돌로 표시합니다.
4. 메타와 스티커는 revision을 따로 관리해 서로 다른 종류의 편집이 충돌하지 않게 합니다.
5. 충돌 화면에서는 서버 내용과 이 기기 내용을 모두 보여 주고 사용자가 하나를 고릅니다. 자동 병합은 같은 필드를 건드리지 않았다는 증거가 있을 때만 후속으로 검토합니다.

## 기존 로컬 자료의 첫 동기화

1. 로그인 뒤 서버 상태를 먼저 읽습니다.
2. 서버 행이 없고 로컬 값만 있으면 로컬 값을 새 서버 행으로 올립니다.
3. 서버와 로컬 값이 모두 있고 같으면 서버 revision을 로컬 캐시에 기록합니다.
4. 둘 다 있으면서 다르면 어느 쪽도 덮어쓰지 않고 충돌 선택 화면을 엽니다.
5. 서버 저장을 확인한 뒤에도 로컬 값을 오프라인 캐시로 유지합니다. 삭제·초기화는 이 마이그레이션에 포함하지 않습니다.

## 구현 범위와 검증

- Supabase 마이그레이션과 수동 검증 SQL
- 공통 타입·검증·revision 충돌 판정
- 웹 서버 저장소와 로컬 캐시 어댑터
- 모바일 계정별 파일 캐시와 서버 동기화 어댑터
- 오프라인 큐, 재시도, 계정 전환 중 늦은 응답 차단
- 웹↔모바일 왕복, 같은 필드 충돌, 다른 계정 격리, 삭제된 캡처 참조 차단 테스트
- 운영 적용 전 로컬 Supabase 또는 격리된 시험 환경에서 마이그레이션·RLS·롤백 검증

완료 판정은 웹에서 저장한 메모와 스티커가 모바일 재로그인 후 나타나고, 모바일 변경이 웹에 반영되며, 충돌과 오프라인 재시도에서 자료가 조용히 사라지지 않을 때입니다.

## 적용 경계

이 문서는 구현·운영 적용 전 결재 자료입니다. 데이터베이스 마이그레이션 파일을 만들거나 운영 데이터에 적용하지 않았습니다. 승인 뒤에도 `마이그레이션 작성·격리 검증`과 `운영 적용`을 별도 단계로 기록합니다.

추천안은 두 보조 테이블과 revision 기반 명시적 충돌 처리입니다. 기존 캡처 스키마를 건드리지 않고, 웹·모바일의 독립 편집을 조용히 덮어쓰지 않는 가장 작은 구조입니다.
